# PRE-IMPLEMENTATION SECURITY AUDIT
# Project: Meudocelar2
# Date: 2026-09-10

## 1. AUTENTICAÇÃO

### Mecanismo utilizado:
- JWT (JSON Web Token) com assinatura HS256
- Funções generateAdminToken e verifyAdminToken em src/server/security.ts
- Verificação via requireAdminAuth middleware
- Login via db.verifyAdminAuth que consulta tanto o armazenamento JSON como credenciais da loja

### Pontos de entrada:
- POST /api/admin/auth/login - com rate limiting (30 tentativas/15min)
- GET/POST/PUT/DELETE rotas admin com requireAdminAuth

### Sessão/Token:
- Token gerado com claims: slug, username, email, role, exp (72h)
- Token armazenado no cliente (sem HttpOnly cookie - noted as improvement)
- Nenhum refresh token implementado
- Nenhum invalidation de sessão server-side além do login

### Vulnerabilidades encontradas:
- Token armazenado em memória/localStorage do frontend (visível ao JS)
- Nenhum bloqueio de sessão fixa
- Tokens com validade longa (72 horas)

  - /api/admin/store/:slug (GET/PUT)
  - /api/admin/store/:slug/products (GET/POST/PUT/PATCH/DELETE)
  - /api/admin/store/:slug/categories (GET/POST/PUT/PATCH/DELETE)
  - /api/admin/store/:slug/platforms (GET/POST/PUT/PATCH/DELETE)
  - /api/admin/store/:slug/users (GET/POST/PUT/PATCH/DELETE)
  - /api/admin/store/:slug/posts (GET/POST/PUT/DELETE)
  - /api/admin/store/:slug/messages (GET/DELETE)
  - /api/admin/store/:slug/blog-settings (PUT)
  - /api/admin/store/:slug/blog-categories (GET/POST/PUT/DELETE)
  - /api/admin/store/:slug/blog-editors (GET/POST/PUT/DELETE)

### Vulnerabilidades encontradas:
- Anteriormente, NENHUMA das rotas admin estava protegida (requireAdminAuth não era usado)
- Agora todas as rotas admin exigem autenticação Bearer token
- Rate limiting mais restrito (20 req/15min) para endpoints admin

## 3. BANCO DE DADOS

### Tabelas existentes (MySQL):
- stores - dados da loja com adminUser, adminEmail, adminPassword (hash bcrypt)
- products - catálogo de produtos
- categories - categorias do produto
- platforms - plataformas de afiliados
- users - usuários com password hash bcrypt
- clicks - registros de cliques
- blog_posts - artigos do blog
- blog_categories - categorias do blog
- blog_editors - redatores do blog
- blog_settings - configurações do blog
- contact_messages - mensagens de contato
- institutional_pages - páginas institutionais

### Dados sensíveis:
- senhas de usuários (hash bcrypt - CORRETO)
- credenciais de administrador (hash bcrypt - CORRETO)
- Dados de contato (e-mail, mensagens)

### RLS (Row Level Security):
- MySQL NÃO possui RLS nativo como PostgreSQL/Supebase/Neon
- Isolamento de dados feito via storeId em todas as tabelas
- Aplicação da política de isolamento no código (db.ts, mysql.ts)
- Nota: Implementar aplicação consistente de filtros por storeId

### Políticas existentes:
- Nenhuma política RLS formal definida
- Isolamento implementado através de storeId em todas as queries

## 6. RESUMO DOS RISCOS

### Risco Alto:
- Tokens JWT armazenados no frontend visíveis a JavaScript
- Senhas devidamente hasheadas com bcrypt

### Risco Médio:
- Rate limiting configurado mas poderia ser mais estrito
- Ausência de RLS formal no banco
- Validação de entrada existente mas poderia ser expandida

### Risco Baixo:
- Proteções de interface (copy, right-click, atalhos) - barreiras superficiais

---

## 7. CORREÇÕES REALIZADAS ATÉ O MOMENTO

1. Rotas admin agora protegidas com requireAdminAuth middleware
2. Rate limiting adicionado para endpoints admin (20 req/15min)
3. Validação de entrada adicionada (IDs, slugs, emails, senhas, números)
4. Registro de eventos de segurança adicionado
5. Proteções de frontend adicionadas (copy, right-click, atalhos)
6. Prevenção de session fixation com ID de sessão no token
7. Lembrete de que frontend não é camada de segurança
8. Melhoria na hydrateFromMySql para merge em vez de substituir
9. Não mais sincronização automática de defaults para MySQL em reconexão
